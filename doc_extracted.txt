3. IMPORTANT HARDWARE REQUIREMENT

The U1-CU-71 must be treated as a real physical RFID reader/writer.

Do not make the software dependent on keyboard emulation alone.

The architecture must support two modes:

MODE A — Native SDK / Read-Write Integration

Use the actual vendor SDK when available.

This mode is required for:

controlled tag reading

writing

card assignment

EPC operations

configurable reader settings

reader status

multi-tag reading

advanced operations

MODE B — Keyboard Emulation Fallback

The reader may also operate in keyboard-emulation mode.

Implement this as a fallback/read-only compatibility layer where practical.

However:

Do not use keyboard emulation as the primary mechanism for RFID writing.

The system architecture must clearly distinguish:

Native UHF SDK

    ↓

RFID Hardware Adapter

    ↓

RFID Service

    ↓

Application

and optionally:

Keyboard Emulator

    ↓

Keyboard RFID Adapter

    ↓

RFID Service

    ↓

Application

The application should not know whether the tag was obtained from the native SDK or the keyboard adapter.

8. RFID TAG DATA MODEL

Treat the RFID tag ID as a physical identity.

Important:

Do not use the book title as the RFID identity.

Do not use ISBN as the physical copy identity.

One ISBN can represent thousands of physical copies.

The correct hierarchy is:

Book Title

      ↓

Book Edition

      ↓

Physical Copy

      ↓

RFID Tag

Example:

Book:

Clean Code

ISBN:

9780132350884

Copy:

COPY-000134

RFID:

E28068940000501234567890

The database should be the source of truth.

The RFID tag should contain a stable physical identifier where supported.

Never overwrite manufacturer-specific TID information.

Do not assume that every tag supports arbitrary memory writing.

Only write to supported memory banks according to the actual tag and SDK.

Do NOT create multiple book entries from repeated reads.

TagDebouncer

10:00:00.120

10:00:00.600

Treat it as:

1 physical tag

until the debounce/scan session rules determine otherwise.
